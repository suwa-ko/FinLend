## 1. 项目概述

### 1.1 项目背景

「综合设计 1」课程要求团队协作完成一个**基础的「借贷软件平台」**，重点在于需求分析、系统设计与工程协作能力的训练。

### 1.2 项目定位

本项目是一个**基础的借贷软件平台**：用户注册后在线申请借款，系统进行审批，审批通过后放款，用户按还款计划偿还本金与利息；管理员在后台管理用户、贷款产品、审批流程与逾期催收。

项目以「**业务流程跑通 + 关键业务规则正确**」为核心目标，是综设项目，**不面向真实放贷经营**。

### 1.3 项目目标

| 目标类型 | 具体目标                                                                                   |
| -------- | ------------------------------------------------------------------------------------------ |
| 功能目标 | 实现「注册 → 实名认证 → 借款申请 → 审批 → 放款 → 还款 → 结清」完整业务闭环（见 §7.2）      |
| 技术目标 | 采用前后端分离 + 单体后端分层架构，金额使用 `Decimal`，鉴权使用 JWT，具备统一返回/异常处理 |
| 协作目标 | 4 人按模块分工、接口契约先行、Git 分支协作，每人有可展示的代码贡献                         |
| 交付目标 | 可运行演示系统 + 需求/设计/启动等配套文档 + 答辩演示材料                                   |

### 1.4 项目范围

| 类别            | 内容                                                                          |
| --------------- | ----------------------------------------------------------------------------- |
| 本期实现（MVP） | 用户/认证、贷款产品、借款申请、审批、放款、还款计划、还款、逾期罚息、后台管理 |
| 本期预留        | 信用评分、授信额度动态计算、基于信用分的自动风控（仅预留接口与字段）          |

> 本项目为**综设项目**，与商业落地项目的本质区别在于：不以盈利为目的、不面向真实用户、不接入真实资金、不承担真实金融合规义务。

## 2. 技术可行性分析

### 2.1 技术需求评估

#### 2.1.1 系统功能技术评估

根据《02-功能需求分析》，系统需实现的核心功能及所需关键技术如下：

| 核心功能           | 关键技术点                                                           | 技术难度 |
| ------------------ | -------------------------------------------------------------------- | -------- |
| 注册/登录/鉴权     | JWT、BCrypt 密码加密、Redis 验证码与令牌黑名单                       | 低       |
| 贷款产品管理       | CRUD、上下架状态管理                                                 | 低       |
| 借款申请与审批     | 审批状态机、乐观锁并发控制                                           | 中       |
| 利息计算与还款计划 | 等额本息/等额本金/先息后本三种算法、`Decimal` 金额精度、最后一期平账 | 高       |
| 放款与账户         | 数据库事务、行级锁/乐观锁防超扣、账户流水                            | 中       |
| 还款与逾期         | 定时任务逾期检测、罚息计算、提前还款规则                             | 中       |
| 后台管理           | 分页查询、统计报表、权限控制                                         | 中       |

**评估结论**：所有功能均有成熟的技术方案支撑，无不可实现的技术难点；难度主要集中在对**业务规则正确性**（利息、审批、逾期）的把控上，属于可通过设计与测试保证的可控风险。

#### 2.1.2 硬件与软件资源评估

| 资源类型 | 需求                                              | 评估结果                 |
| -------- | ------------------------------------------------- | ------------------------ |
| 硬件     | 团队每人 1 台个人电脑                             | 完全满足                 |
| 运行时   | Python 3.11+、Node.js 18+、MySQL 8.0、Redis       | 全部开源免费，可本地运行 |
| 开发工具 | Codex、DSH、PyCharm、VS Code、Git、Apifox/Postman | 免费版即可               |
| 云资源   | 云服务器/内网穿透                                 | 非必需                   |

**评估结论**：硬件与软件资源**完全满足**课程项目需求，无资源瓶颈，无许可证成本。

### 2.2 技术实现途径

#### 2.2.1 现有技术的适用性分析

根据《01-技术栈分析与选型》，本项目全部采用**成熟主流技术**：

| 技术层    | 选型         | 成熟度 | 集成难度 | 功能匹配度                     |
| --------- | ------------ | ------ | -------- | ------------------------------ |
| 后端框架  | FastAPI      | ★★★★★  | 低       | 原生支持 RESTful、自动接口文档 |
| 后端 ORM  | SQLAlchemy 2 | ★★★★★  | 低       | 覆盖全部数据访问需求           |
| 数据校验  | Pydantic v2  | ★★★★★  | 低       | 请求/响应模型校验              |
| 前端框架  | Vue 3 + Vite | ★★★★★  | 低       | 单页应用、组件化               |
| UI 组件库 | Element Plus | ★★★★★  | 低       | 表格/表单/弹窗组件丰富         |
| 数据库    | MySQL 8.0    | ★★★★★  | 低       | 事务与金额精度支持良好         |
| 缓存/会话 | Redis        | ★★★★★  | 低       | 验证码、令牌黑名单             |

**评估结论**：所选技术均为**成熟、主流、资料丰富**的方案，与系统功能需求高度匹配，集成难度低。

#### 2.2.2 新技术的研发难度评估

本项目**不引入任何新技术研发**，全部基于现有成熟技术做集成开发。对于团队成员尚不熟悉的部分（如 SQLAlchemy、JWT、Decimal 金额处理），属于**学习成本**而非研发风险，可通过课程教学、官方文档与团队结对解决。

**评估结论**：无新技术研发难度，风险可控。

### 2.3 技术风险与挑战

#### 2.3.1 技术更新换代风险

本项目周期短，所选技术栈均为长期主流技术，不存在短期被淘汰的风险。即使未来技术演进，由于项目采用**分层架构 + 接口抽象**，核心业务逻辑（利息、审批、还款）与技术框架耦合度低，具备良好的可维护性。

**评估结论**：技术更新换代风险**很低**，可忽略。

#### 2.3.2 技术实施的可行性

| 潜在挑战                     | 应对措施                                                                      |
| ---------------------------- | ----------------------------------------------------------------------------- |
| 三种还款方式的利息计算正确性 | 用 `Decimal` 计算、最后一期平账、编写单元测试用例覆盖典型金额                 |
| 金额并发超扣/超额            | 数据库事务 + 乐观锁（版本号）/行级锁，见《03-数据库设计》§4.3                 |
| 逾期罚息按日计算             | 定时任务（APScheduler）每日执行，公式明确                                     |
| 前后端接口对接               | 接口契约先行，FastAPI 自带 Swagger 文档，统一返回结构 `{code, message, data}` |
| 团队对部分技术不熟悉         | 选型均为资料丰富的主流技术；全栈「胶水」角色负责联调与技术支援                |

**评估结论**：技术实施可行，主要挑战均有明确预案。

### 2.4 技术可行性结论

> **技术可行**。技术栈成熟可靠、完全免费、学习曲线平缓，所有核心功能均有成熟的实现路径，技术风险可控。

| 成本类别   | 详细说明                                      | 预期成本                       |
| ---------- | --------------------------------------------- | ------------------------------ |
| 软件与工具 | Python/FastAPI/Vue/MySQL/Redis 等全部开源免费 | **0 元**                       |
| 硬件设备   | 使用团队自有电脑                              | **0 元**                       |

### 3.2 投入产出（收益）分析

| 审查维度     | 本项目情况                                                   | 结论                             |
| ------------ | ------------------------------------------------------------ | -------------------------------- |

| 知识产权     | 全部采用开源技术，遵守各开源协议（MIT/Apache-2.0/BSD 等）    | 合规，无商用授权纠纷             |
| 第三方组件   | 使用开源框架与组件库，不侵犯他人专利/版权                    | 合规                             |
| 学术诚信     | 文档与代码原创，引用第三方资料注明来源；标注AI生成内容       | 符合课程要求                     |

#### 4.1.2 合规风险评估与对策

| 潜在合规风险               | 应对措施                                           |
| -------------------------- | -------------------------------------------------- |
| 演示时误用真实个人信息     | 一律使用虚构 seed 测试数据，演示不展示真实敏感信息 |
| 开源协议不明导致的合规争议 | 记录依赖清单，确认各依赖的开源协议并遵守           |

**评估结论**：法律合规风险**很低**，仅需保持合规意识即可。

### 4.2 操作实施的可能性

#### 4.2.1 人力资源与培训需求

根据《04-团队分工与协作》，本项目 4 人分工明确、工作量均衡：

| 角色       | 人数 | 职责                                               |

3. **联调节奏**：前后端联调，全栈记录问题清单并闭环。
4. **进度同步**：每周简短同步，全栈汇总到进度表。

**评估结论**：流程清晰、可执行，支持 4 人高效并行。

## 5. 时间与市场可行性分析

### 5.1 时间规划与项目里程碑

#### 5.1.1 项目总体时间规划

将项目划分为四个阶段：

| 阶段        | 内容                                                     | 预估工期         |
| ----------- | -------------------------------------------------------- | ---------------- |
| M1 奠基     | 项目脚手架 + 数据库建表 + 用户注册/登录（JWT）+ 接口契约 | 约 2 周          |
| M2 申请链路 | 贷款产品管理 + 借款申请 + 审批流程                       | 约 3 周          |
| M3 核心业务 | 放款 + 还款计划生成 + 还款/逾期处理                      | 约 3～4 周       |
| M4 收尾演示 | 后台看板 + 消息通知 + 联调 + 演示材料                    | 约 2～3 周       |
| **合计**    | 有效开发周期（含缓冲）                                   | **约 10～12 周** |

#### 5.1.2 关键里程碑与进度控制

| 里程碑  | 验收标准                                                                       |
| ------- | ------------------------------------------------------------------------------ |
| M1 完成 | 后端 `/health` 可跑，数据库建表 + seed 可登录，前端可启动，注册/登录全链路跑通 |
| M2 完成 | 产品 + 申请 + 审批链路联调通过                                                 |
| M3 完成 | 放款、还款计划、还款、逾期罚息全部跑通，利息计算用例通过                       |
| M4 完成 | 后台看板 + 消息通知完成，演示材料齐备，文档整合完成                            |

**进度控制**：采用敏捷迭代方式；每个里程碑设检查点，未达标不进入下一阶段。

**评估结论**：项目规模与课程周期匹配，时间安排合理、留有余量。

### 5.2 市场需求与竞争分析

> 本项目为课程项目，**不以商业化为目标**。

#### 5.2.1 选题价值（目标需求评估）

| 维度       | 分析                                                                       |
| ---------- | -------------------------------------------------------------------------- |
| 选题普适性 | 借贷/金融是典型的信息化场景，业务规则清晰、受众容易理解                    |
| 知识覆盖度 | 覆盖认证、鉴权、事务、并发、定时任务、报表等 Web 全栈核心知识点            |
| 就业相关度 | 金融科技是热门方向，借贷系统的利息计算、审批流、风控概念与真实业务高度相关 |
| 用户痛点   | 解决「借款申请—审批—放款—还款」线上化管理的典型需求                        |

#### 5.2.2 同类项目对比与差异化定位

## 6. 结论与建议

### 6.1 可行性结论汇总

| 维度       | 结论 | 核心依据                               |
| ---------- | ---- | -------------------------------------- |
| 技术可行性 | 可行 | 成熟主流技术栈，无新技术研发，风险可控 |
| 经济可行性 | 可行 | 零货币成本，投入产出比高               |
| 法律可行性 | 可行 | 教学演示系统，不触发真实金融合规义务   |
| 操作可行性 | 可行 | 4 人分工均衡，流程清晰，风险有预案     |
| 时间可行性 | 可行 | 里程碑明确，工期与课程周期匹配         |
| 市场可行性 | 可行 | 选题价值高、差异化明显                 |

### 6.2 综合结论

> **本项目在技术、经济、法律、操作、时间与选题等各维度均可行，建议按计划立项并推进实施。** 项目的核心风险在于**利息计算等业务规则的正确性**与**团队协作进度**，均已有明确的应对预案，不会构成实施障碍。

### 6.3 实施建议

1. **严守奠基阶段**：先统一环境、建库、搭骨架、定接口契约，再分头并行，避免返工。
2. **业务规则优先**：利息计算、审批状态机、逾期罚息是答辩重点，优先投入并配套单元测试。
3. **接口契约先行**：以 FastAPI `/docs` 为唯一契约来源，前后端按契约并行、不等不靠。
4. **里程碑强验收**：M1~M4 检查点不达标准不进入下一阶段，全栈负责跟踪与预警。
5. **风险预留缓冲**：为 M3预留最充足时间，防止进度挤压导致核心功能质量下降。
6. **合规与诚信**：全程使用虚构测试数据，引用注明来源，注明AI内容，保持学术诚信。
