# 00 · 借贷软件平台（FinLend）可行性分析报告

> 项目类型：「综合设计 1」课程设计项目
> 初稿日期：2026年9月7日 · 撰写人：王晨宇
> 修订日期：2026年9月22日 · 版本：v1.1
> 工具使用：DeepSeek Harness、Codex
> 状态：设计阶段评估；目前仓库仅含文档，以下能力和验收指标均为计划，尚无实现或测试结果。

## 1. 项目概述

### 1.1 背景与目标

项目训练需求分析、系统设计、团队协作和软件验证能力，使用虚构身份与模拟资金，完成“注册认证 → 借款申请 → 审批签约 → 放款 → 还款 → 结清”的业务闭环。

本学期交付 Web 用户端、Web 管理端以及 uni-app 安卓借款人 App，三端共用后端与数据库。重点是金额正确、状态可控、跨端一致，并可在本地课程环境重复演示。

### 1.2 范围与交付物

| 类别     | 内容                                                                                                                                                                        |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 必须交付 | 三端相应页面、认证及续期、模拟实名/测试图片、产品、申请/签约/审批、模拟放款、还款与提前结清、逾期、站内消息，**Web 基础后台管理**（用户/产品/审批/放款/逾期列表）及 **APK** |
| 配套交付 | 完整迁移与 seed、接口契约、测试记录、安装部署/用户手册、答辩材料                                                                                                            |
| 可选增强 | 报表图表与导出、催收备注、模拟充值页面                                                                                                                                      |
| 后续扩展 | 信用评分/动态额度、多源融合、小程序、厂商推送                                                                                                                               |
| 本期排除 | 真实资金、真实征信/身份核验、真实个人敏感资料采集、银行卡自动扣款                                                                                                           |

业务边界和默认值以 [02-功能需求分析](02-功能需求分析.md) 为准；风控本期仅有黑名单规则与明确标注的模拟接口。

### 1.3 评估依据与待验证假设

| 假设                                      | 验证时间/责任              | 不成立时的处理                                    |
| ----------------------------------------- | -------------------------- | ------------------------------------------------- |
| 4 人持续投入，保留 12 周有效开发窗口      | 第 1 周，全员核对课程安排  | 优先移除可选增强，重排工期；安卓 APK 仍为必需交付 |
| 至少一人能承担 uni-app 开发，另一人可协助 | M1，前端/全栈验证登录 APK  | 安排结对与页面分担，在 M1 暴露学习风险            |
| 可获得 Android 真机和可互访的局域网       | M1，全栈验证安装及 API     | 使用团队现有设备和已验证网络，不拖到答辩前        |
| MySQL/Redis 与后端可在开发机运行          | M1，A/B 验证连接和迁移     | 统一 WSL2/容器或本地服务配置                      |
| 验收接受模拟身份、资金和未接入真实风控    | 范围说明提交课程评审时核对 | 将额外要求作为变更评估，不宣称已获教师认可        |

## 2. 技术可行性

### 2.1 方案与实现风险

| 能力      | 技术方案                                        | 风险/验证                                           |
| --------- | ----------------------------------------------- | --------------------------------------------------- |
| 后端 API  | FastAPI + Pydantic + SQLAlchemy + PyMySQL       | 同步数据库访问与请求模型兼容；M1 完成最小链路       |
| Web       | Vue 3 + Vite + Element Plus                     | 用户与管理页面工作量；由前端主责                    |
| 安卓      | uni-app（Vue 3）+ uni-ui + Pinia                | 组件不能直接复用 Web；M1 必须首次打包并真机调用 API |
| 会话/上传 | JWT access token + 可轮换刷新令牌、私有测试附件 | 轮换、吊销、图片归属需实际验证                      |
| 资金/利息 | Decimal、合同快照、事务及唯一键                 | 金额、幂等和并发是高风险项，M3 专项验收             |
| 逾期/提醒 | 单实例调度、计费日期、事件去重                  | 宕机补算与重复执行需要测试，不能只描述为“每日定时”  |
| 数据      | MySQL 业务/会话/附件元数据；Redis 验证码和限流  | Redis 故障不得使鉴权或交易校验失效                  |

技术栈选择主要依据团队 Vue/Python 学习路径和课程规模，未进行框架性能横向实测。具体依赖、构建环境及接口约束见 [01-技术栈分析与选型](01-技术栈分析与选型.md)。

### 2.2 主要技术风险

| 风险                   | 影响                       | 负责人    | 应对与验收证据                                       |
| ---------------------- | -------------------------- | --------- | ---------------------------------------------------- |
| 月供舍入、费率单位混淆 | 错误应还金额               | B，A 复核 | 固定 Decimal 规则，三种方式/零利率/最后一期基准用例  |
| 余额与授信混用         | 放款方向错误、超额授信     | B         | 模拟放款增加现金；授信由未还本金计算；事务与对账验证 |
| 重复请求/罚息任务重跑  | 重复扣款/收费              | B         | 数据库幂等记录、计费日期、并发及漏跑测试             |
| Web/安卓工作挤压       | APK 延期                   | 前端/全栈 | Web、安卓分主责，M1 打包，M2 起跨端联调              |
| 依赖/构建工具不兼容    | 无法重现环境               | A/全栈    | 记录实测版本并锁定，不能仅写“最新版”                 |
| 上传或鉴权越权         | 暴露测试资料、错误账户操作 | A         | 文件所有权、会话吊销、角色隔离负向验证               |

**技术结论：有条件可行。** 不需要研发新算法或分布式基础设施，但跨端交付、账务一致性和团队学习成本仍需通过 M1/M3 证据验证。

## 3. 经济可行性

本项目不以商业收益衡量成果。现金支出与人力时间分开估算，不能用“课程作业”推导人力没有成本。

| 成本项           | 规划口径                                               | 依据/限制                                                          |
| ---------------- | ------------------------------------------------------ | ------------------------------------------------------------------ |
| 现有电脑、手机   | 复用已有设备，新增采购目标为 0 元                      | 真机可用性尚需 M1 验证                                             |
| 框架与数据库     | 采用可用于教学的版本                                   | 逐项记录许可证；不能将 Redis、IDE 或全部工具统一断言为相同开源许可 |
| 本地部署         | 优先局域网演示，不要求购买云服务                       | 公网域名、证书、云资源如新增需单独估算                             |
| 安卓打包         | 先验证现有 HBuilderX/构建服务可用额度                  | 网络、账号或构建服务限制纳入 M1 记录，不预先承诺免费不限量         |
| 辅助开发工具/API | 可选费用，按实际使用记录                               | 不将订阅/API 费用计为 0；无付费工具也应能完成项目                  |
| 人力             | 规划假设 4 人 × 12 周 × 每周 6–8 小时，共 288–384 人时 | 含学习、编码、联调和文档；由全员在第 1 周核对                      |

以上是预算假设，非采购报价或已经发生的费用。学习收益包括状态机、财务计算、接口协作和 APK 交付；没有货币化数据，不计算数值投资回报率。课程后如继续维护，仍会产生维护工时和可能的服务费用。

**经济结论：在复用设备、本地部署、控制可选付费工具的条件下，新增现金支出可以较低；主要约束是时间。**

## 4. 数据、许可与操作可行性

本次评估限于封闭教学演示，不构成真实金融业务的法律意见。使用开源或免费组件也不自动证明许可证兼容。

| 检查项    | 本期执行约定                                                   | 证据                                         |
| --------- | -------------------------------------------------------------- | -------------------------------------------- |
| 身份/资金 | 虚构姓名/证件图片/银行卡、模拟账户，不接真实支付               | seed、界面模拟标识、演示说明                 |
| 数据访问  | 按用户和角色鉴权，附件非公开存储，日志不输出令牌或完整证件信息 | 权限与日志检查                               |
| 依赖许可  | 记录实际版本及许可证，保留要求的声明                           | 依赖清单及 THIRD_PARTY_NOTICES（实现时产出） |
| 学术引用  | 保留参考来源、工具使用说明，按课程要求标注辅助生成内容         | 文档引用及课程提交材料                       |
| 变更边界  | 若转向真实用户或资金，重新评估数据、安全和相关业务要求         | 新版本范围评审                               |

人员责任见 [04 §2](04-团队分工与开发规范.md#2-角色与产出)。前端主责 Web，全栈主责安卓，A/B 负责各自业务模型、迁移与测试；不能把数据库、安卓、所有测试和所有文档都压到一个人。

## 5. 工期与交付可行性

### 5.1 本学期 12 周基线

周数为有效开发周，不是已确认的课程日期。第 1 周记录实际起止日期，后续按同一基线跟踪。

| 阶段    | 周次/时长         | 主要交付                                  | 退出条件                                      |
| ------- | ----------------- | ----------------------------------------- | --------------------------------------------- |
| M1 奠基 | 第 1–2 周，2 周   | 双端骨架、认证、核心表迁移/seed、最小 APK | 真机登录/续期成功，接口和构建版本冻结         |
| M2 申请 | 第 3–5 周，3 周   | 模拟实名/上传、产品、试算、申请/审批/签约 | 双端申请与 Web 审批闭环，拒绝和超时路径可验证 |
| M3 账务 | 第 6–9 周，4 周   | 放款、计划、还款/提前结清、逾期、消息     | 计算/幂等/并发/对账验证通过                   |
| M4 交付 | 第 10–12 周，3 周 | APK、使用/部署手册、双端回归与演示        | 核心阻塞缺陷为零，安装、恢复和演示证据完整    |

第 12 周保留给阻塞缺陷与演示缓冲，不安排新功能。各阶段详细检查点见 [04 §8](04-团队分工与开发规范.md#8-里程碑检查点)，安卓任务见 [06 §2.7](06-扩展与演进规划.md#27-本学期实施计划与验收)。

### 5.2 进度控制与延期处理

每天文字同步，M2 起每两天联调；每周核对剩余工作与投入工时。若关键链路落后一个工作周，先暂停报表图表、导出和可选 UI 优化，将人力移到 P0。金额正确性、权限和安卓交付不能靠删除验收来按期完成。

检查点未通过时保留未完成状态并记录补救计划，独立任务可继续；不将“进入下一阶段”误作“所有前序工作已完成”。

### 5.3 选题价值与局限

平台适合展示多角色状态流转、事务、Decimal 金额处理和跨端 API 复用。该判断基于课程训练目标，未开展市场调研，不能推出商业竞争力、真实风控效果或经营可行性。答辩重点是规则与实现证据，不是宣称能够运营真实借贷业务。

## 6. 结论与启动条件

建议按本学期 Web + 安卓范围推进，结论为**有条件可行**：

1. M1 验证实际可用工时、真机、打包链路及双端登录；
2. 用 [02](02-功能需求分析.md) 的统一规则实施，按 [03](03-数据库设计.md) 的约束和事务保证账务；
3. M3 完成金额、幂等、计费补算及并发证据；M4 完成真实安装和可重复演示；
4. 多数据融合保持后续预留，可选增强不得挤占 P0。

这些条件尚未经过代码验证，应随里程碑证据更新本报告，而不是直接将本报告当作通过验收的证明。
