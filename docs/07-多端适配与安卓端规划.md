# 07 · 多端适配与安卓端规划

> 借贷类产品在真实场景中以手机为主入口，本文档说明本项目「Web 优先 + API 预留多端」的策略、为什么后端无需重构，以及安卓端（综设2）采用 uni-app 的技术方案与落地路径。

---

## 1. 背景与结论

### 1.1 背景

贷款产品的真实用户主要在手机端完成「申请借款、查看还款计划、还款」等高频操作，网页端更多承担运营与管理职责。因此「是否需要适配手机端」是绕不开的设计问题。

### 1.2 结论

| 问题                      | 结论                                                                |
| ------------------------- | ------------------------------------------------------------------- |
| 后端需要重构吗？          | **不需要**。现有架构天然客户端无关，安卓端可直接复用同一套 API      |
| 本期（综设1）做安卓端吗？ | **不做**。本期交付 Web 端（用户端 + 管理端）                        |
| 安卓端什么时候做？        | 列为**综设2 扩展方向**，与信用评分、动态额度同期                    |
| 用什么技术做？            | **uni-app**（复用 Vue 3 技能，一套代码可编译到 H5 / 安卓 / 小程序） |
| 本期要为此做什么？        | **接口预留**（§5），避免综设2 返工                                  |

> 核心判断依据：**先做 Web 完全不影响后期加 App**，因为客户端与后端之间只通过 RESTful API 通信。

---

## 2. 为什么后端不需要重构

本项目的总体架构是「前后端分离 + 单体后端 + RESTful API」，这一架构的关键特性是**客户端无关**：

- 后端只暴露 HTTP + JSON 接口，不关心调用方是浏览器、安卓 App 还是小程序；
- 统一返回结构 `{code, message, data}` 与 `/api/v1` 版本前缀，为多客户端提供了稳定的契约；
- JWT 鉴权基于请求头，天然与客户端类型解耦；
- FastAPI 自带的 OpenAPI 文档（`/docs`）可直接作为各端的接口契约来源。

```
┌──────────────────────────┐
│ Web SPA                  │  Vue 3 + Element Plus
│ （用户端 + 管理端）        │
└────────────┬─────────────┘
             │
             │   HTTP / JSON  +  JWT
             │
┌────────────▼─────────────┐        ┌───────────────┐
│ 后端 FastAPI  /api/v1     │───────►│ MySQL         │
│ 路由 → 业务 → 数据访问     │        │ Redis         │
└────────────▲─────────────┘        └───────────────┘
             │
┌────────────┴─────────────┐
│ 安卓端 / H5 / 小程序       │  uni-app（综设2）
└──────────────────────────┘
```

**结论**：同一套后端同时服务 Web 端与未来的安卓端，无需为多端拆分服务。

## 3. 客户端方案选型

### 3.1 方案对比

| 方案                      | 做法                                              | 成本           | 是否复用现有技能 | 评价                        |
| ------------------------- | ------------------------------------------------- | -------------- | ---------------- | --------------------------- |
| A. 响应式 Web             | 现有 Vue 加自适应布局，手机浏览器可用             | ⭐ 低          | ✅ Vue           | 性价比高，但无原生 App 体验 |
| B. PWA                    | A + manifest + service worker，可「添加到主屏幕」 | ⭐⭐ 低-中     | ✅ Vue           | 演示效果好，仍非真 App      |
| C. **uni-app**            | 一套 Vue 语法代码 → 编译 H5 / 安卓 / 小程序       | ⭐⭐⭐ 中      | ✅ **Vue**       | **本项目选定**              |
| D. Flutter / React Native | 跨平台原生渲染                                    | ⭐⭐⭐⭐ 中-高 | ❌ 需学 Dart/RN  | 性能好，但技能栈外          |
| E. 原生安卓（Kotlin）     | 真原生体验                                        | ⭐⭐⭐⭐⭐ 高  | ❌ 需学 Kotlin   | 等于多维护一套客户端        |

### 3.2 选定 uni-app 的理由

1. **技能复用度最高**：uni-app 使用 Vue 语法与组件化思想，团队已有的 Vue 3 经验可直接迁移，无需学习全新语言。
2. **一套代码多端运行**：可同时编译出 H5、安卓 App、微信小程序，边际成本低。
3. **生态与资料友好**：国内主流方案，中文文档完善、社区活跃，遇到问题容易检索。
4. **答辩展示价值高**：「一套代码多端运行」是很好的课程项目亮点，且能体现工程化思维。

### 3.3 为什么不选原生安卓 / Flutter

| 方案               | 不选理由                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 原生安卓（Kotlin） | 需要另一套技术栈（Kotlin + Android SDK），4 人团队学习成本高，等于多维护一套客户端，会挤压利息计算、审批流等答辩重点的投入 |
| Flutter            | 需学习 Dart；无法复用现有 Vue 组件与生态，团队上手慢                                                                       |
| React Native       | 需掌握 React 体系，与团队现有 Vue 技能不匹配                                                                               |

### 3.4 用户端与管理端的技术分工

本项目两端的使用场景差异明显，建议**分别对待**：

| 端               | 使用场景                     | 技术方案                                        |
| ---------------- | ---------------------------- | ----------------------------------------------- |
| 管理端（管理员） | 桌面为主，大量表格/审批/报表 | 保留 **Web + Element Plus**（表格表单能力最强） |
| 用户端（借款人） | 移动为主，申请/还款/通知     | uni-app 侧重移动体验；Web 端可保持响应式兜底    |

> 说明：用户端若在 Web 上做移动适配，建议引入 **Vant**（移动端 Vue 组件库）而非硬套桌面向的 Element Plus。

## 4. 安卓端技术栈

| 层次      | 选型                                        | 对应 Web 端的同类技术 |
| --------- | ------------------------------------------- | --------------------- |
| 框架      | uni-app（Vue 3 语法）                       | Vue 3                 |
| UI 组件库 | uni-ui / uView Plus                         | Element Plus          |
| 状态管理  | Pinia                                       | Pinia                 |
| 网络请求  | `uni.request` 封装                          | Axios                 |
| 本地存储  | `uni.setStorageSync` / `uni.getStorageSync` | localStorage          |
| 路由      | `pages.json` 配置式路由                     | Vue Router            |
| 打包      | HBuilderX / uni-app CLI → APK               | Vite 构建             |

## 5. 后端需要补充的能力（安卓端前置条件）

安卓端不是「另写一个界面」那么简单，以下几项是移动端特有的机制，**建议在本期接口设计时就预留**，否则综设2 会返工。

| #   | 能力                     | 本期现状                             | 需要新增                                                           | 优先级              |
| --- | ------------------------ | ------------------------------------ | ------------------------------------------------------------------ | ------------------- |
| 1   | **令牌刷新机制**         | 单个 JWT，2 小时过期，退出即拉黑     | access token（短）+ refresh token（长），接口 `POST /auth/refresh` | 🔴 高               |
| 2   | **文件 / 图片上传**      | 实名认证「可简化为表单」，无上传接口 | 证件照 / 人脸照片上传接口 + 存储方案（本地或 MinIO/OSS）           | 🔴 高               |
| 3   | **消息推送**             | 仅站内信（需主动刷新）               | 可选：WebSocket 实时推送，或移动端轮询；厂商推送可暂不做           | 🟡 中               |
| 4   | **多端登录策略**         | 未定义                               | 明确同一账号在 Web 与 App 并存的规则；令牌按设备隔离               | 🟡 中               |
| 5   | **接口幂等性**           | 仅「防重复提交申请」                 | 移动网络易断，重试需保证不重复放款 / 重复还款                      | 🟡 中               |
| 6   | **HTTPS 与本地令牌存储** | 未提及                               | 生产环境强制 HTTPS；App 侧令牌存 Keystore 而非明文                 | 🟢 低（课程可简化） |

### 5.1 数据库预留

配合上述能力，综设2 需要新增表（本期可只预留字段说明）：

| 表                | 用途                                           |
| ----------------- | ---------------------------------------------- |
| `t_refresh_token` | 存储刷新令牌（含设备标识、过期时间、是否吊销） |
| `t_file`          | 上传附件元数据（用户、类型、路径、大小、时间） |
| `t_device`        | 设备与推送标识（可选，视是否做推送而定）       |

## 6. 安卓端功能范围

安卓端**只做借款人侧**，管理端仍保留在 Web：

| 模块                       | 安卓端 | 说明                        |
| -------------------------- | ------ | --------------------------- |
| 注册 / 登录                | ✅     | 含 refresh token 自动续期   |
| 实名认证                   | ✅     | 拍照上传证件，比 Web 更自然 |
| 贷款产品浏览 / 详情        | ✅     | —                           |
| 额度试算                   | ✅     | 复用后端计算接口            |
| 提交借款申请               | ✅     | —                           |
| 我的借款 / 还款计划        | ✅     | —                           |
| 还款 / 提前还款            | ✅     | —                           |
| 消息通知                   | ✅     | 站内信 + 可选推送           |
| 账户 / 银行卡 / 个人信息   | ✅     | —                           |
| 后台管理（审批/产品/报表） | ❌     | 保留 Web 桌面端             |

## 7. 与本期（综设1）的边界

| 类别         | 内容                                                          |
| ------------ | ------------------------------------------------------------- |
| 本期**做**   | Web 端完整功能；后端接口**预留**移动端能力（§5 的高优先级项） |
| 本期**不做** | 安卓端本体、推送的完整实现、文件上传的完整实现                |
| 验收说明     | 本期的评分与验收**不依赖安卓端**；安卓端属于综设2 扩展        |

| 阶段              | 交付内容                                                                           |

## 9. 风险与对策

| 风险                               | 对策                                                                 |
| ---------------------------------- | -------------------------------------------------------------------- |
| uni-app 无法复用 Element Plus 组件 | 用户端本就应做移动优先 UI，改用 uni-ui / uView Plus；管理端留在 Web  |
| 一套代码多端表现不一致             | 优先保证 H5 与安卓两端质量，小程序按需再适配                         |
| 后端接口变更影响双端               | 坚持接口契约先行 + `/api/v1` 版本管理；接口只增不改，破坏性变更走 v2 |
| 团队无人做过 uni-app               | 官方中文文档完善；先用 H5 模式快速验证，再打 APK                     |
| 安卓端挤压本期进度                 | 明确安卓端属于综设2，本期不启动，避免范围蔓延                        |
