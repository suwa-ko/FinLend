### ⚠️ 模板自身的一处不一致（需我们决定）

- **目录**（9 章）里**没有**「系统用例设计」；
- **正文**却在「外部接口需求」与「系统功能需求」之间**确有一节「系统用例设计」**，要求「绘出系统的用例图，粗略说明各个用例的作用，粗略描述参与者对用例的使用以及交互」；
- 正文还把「**用例描述**」（含 12 项要素）放在「系统功能需求」之下，而目录的 4.1~4.3 里没有它。

**本框架的处理**：把「系统用例设计」**独立成章**，后续章节顺延，最终为 **10 章**。
理由：用例图与用例清单是需求分析报告的**核心交付物**，独立成章便于评审与查阅；模板正文也给了它完整的写作要求。

## 三、各章写作要点与可复用素材

> 本项目已有 7 份设计文档，**大部分内容可直接改写复用**，不必从零写起。下表「可复用素材」列指明来源。

| 章节                   | 要写什么                                                                                                                                   | 可复用素材                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| 1.1 编写目的           | 为哪个软件产品编写、开发意义与目标、覆盖范围（本期只做综设1 范围）                                                                         | `README` 项目定位、`00-可行性分析报告` §1                               |
| 1.2 项目风险           | 三类风险承担者：任务提出者（课程组/指导教师）、软件开发者（4 人团队）、产品使用者（模拟借款人/管理员）各自承担的风险                       | `00` §风险评估、`04` §6                                                 |
| 1.3 文档约定           | 排版约定、术语约定、**需求编号规则**（如 `FR-01`/`NFR-01`/`UC-01`）、优先级定义（高/中/低）                                                | 需新写（可参考 `05-术语表` 的符号说明）                                 |
| 1.4 预期读者和阅读建议 | 列出读者类型（指导教师、开发者、答辩评委）并给每类读者**阅读建议**                                                                         | 需新写                                                                  |
| 1.5 产品范围           | 产品及其开发目的的简短描述；**不能把项目视图文档整段复制过来**                                                                             | `README`、`00` §1.2/§1.4、`06-扩展与演进规划` §1                        |
| 1.6 参考文献           | 按序排列，每份给出标题/作者/编号或版本/日期/来源                                                                                           | 本项目 `docs/00`~`06` 七份文档 + 技术官方文档                           |
| 2.1 产品的状况         | 属哪种情况（系列下一成员 / 升级品 / 替代品 / 新型自主产品）；与外部系统的关联与接口                                                        | `README`、`06` §1（本项目是最终项目《多数据融合的贷款系统》的前置阶段） |
| 2.2 产品的功能         | **业务层概览**（不展开细节，细节留给第 5 章）；建议用列表或顶层数据流程图                                                                  | `02-功能需求分析` §1/§3                                                 |
| 2.3 用户类和特性       | 区分重要用户类与非重要用户类                                                                                                               | `02` §2（借款人 / 管理员）                                              |
| 2.4 运行环境           | 硬件平台、操作系统与版本、支撑环境与版本、其它软件组件、共存的应用程序                                                                     | `01-技术栈分析与选型` §6、`04` §5 环境表                                |
| 2.5 设计和实现上的限制 | 必须用/避免用的技术、需遵循的规范与标准、企业/法规/标准/硬件/数据格式限制                                                                  | `01` §8「不引入的技术」、`07`… 见 `06` §2.3                             |
| 2.6 假设和约束（依赖） | 假设因素（如"不接入真实支付与征信、全部使用虚构数据"）+ 工期/经费/人员/设备约束                                                            | `00` §3、`06` §4                                                        |
| 3.1 用户界面           | 只写**逻辑特征**（GUI 标准、屏幕布局限制、组件、显示格式、错误信息显示标准），**不写具体对话框布局**                                       | `01` §4、`06` §2.3/§2.4                                                 |
| 3.2 硬件接口           | 与系统硬件接口的特征；**本系统无特殊硬件接口，如实说明"无"即可**                                                                           | 需新写（可写"不适用"）                                                  |
| 3.3 软件接口           | 外部组件名称与版本：操作系统、数据库、工具、函数库、集成的商业组件                                                                         | `01` §3/§4/§5、`04` §5                                                  |
| 3.4 通讯接口           | 网络通讯标准/协议、消息格式、通讯安全或加密、传输速率、同步/异步机制                                                                       | `01` §2/§7、`04` §6（统一返回结构、JWT）                                |
| 4. 系统用例设计        | **用例图** + 用例清单（粗略说明各用例作用、参与者与用例的交互）                                                                            | `02` §3/§5.1/§5.2、可参考已有 Mermaid 流程图                            |
| 5.1 说明和优先级       | 逐条编号的功能需求清单（名称 + 优先级 + 简短说明）；一条需求应对应一条测试用例                                                             | `02` §4 各模块表、§9 优先级（P0/P1/P2）                                 |
| 5.2 激励／响应序列     | 关键功能的「触发事件 → 系统响应」序列                                                                                                      | `02` §5 业务流程图、§8 异常场景                                         |
| 5.3 输入／输出数据     | 每个功能的输入数据、处理（计算）方法、输出数据；数据项需含名称/含义/类型/格式/约束                                                         | `02` §6 业务规则、`03` 表结构                                           |
| 5.4 用例描述           | 按模板 12 项逐条写：用例名、简述、主要参与者、情景目标、前提条件、触发事件、场景描述、异常处理、优先级、使用频率、次要参与者、未明确的问题 | `02` §5、`03` §4（放款事务等）                                          |
| 6.1 性能需求           | 相互合作的用户数量、并发操作数量、响应时间、与实时系统的时间关系、容量（存储器/磁盘/表最大行数）                                           | `02` §7 非功能需求（需**量化**，现有描述偏笼统）                        |
| 6.2 安全措施需求       | 可能发生的损失/破坏/危害，必须采取的安全保护动作，必须预防的危险动作，需遵从的安全标准                                                     | `01` §7、`02` §7                                                        |
| 6.3 安全性需求         | 系统安全性与完整性、个人隐私；用户身份认证与授权需求                                                                                       | `01` §7、`02` §4.1（实名认证/脱敏）、`05` 安全术语                      |
| 6.4 软件质量属性       | 可靠性/可维护性/可扩展性/可测试性/易用性；须**确定、定量、可验证**，并指明相对侧重点                                                       | `02` §7、`06` §3.2 设计原则                                             |
| 6.5 业务规则           | 列出所有操作规则（谁在什么条件下可做什么）——**本身不是功能需求，但会引出功能需求**                                                         | `02` §6（利息/罚息/提前还款/授信/信用评分）——本项目最扎实的一章         |
| 6.6 用户文档           | 随产品交付的用户文档及其格式：安装指南、用户手册、在线帮助、使用教程                                                                       | `04` §5（本项目实际交付文档清单）                                       |
| 7. 词汇表              | 业务层专业术语（尽量用非计算机术语解释），缩写需给外文原词                                                                                 | **`05-术语表` 可直接改造复用**（去掉"本项目"列即可）                    |
| 8. 数据定义            | 所有数据元素与结构：含义、类型、大小、格式、计量单位、精度、取值范围；每项给中文名 + 英文名                                                | `03-数据库设计` 全部表结构；注意需求阶段应写**逻辑数据项**              |
| 9. 分析模型（可选）    | 数据流程图、类图、状态转换图、实体-关系图                                                                                                  | `02` §5.2 状态机、`03` §2 ER 图（均已是 Mermaid）                       |
| 10. 待定问题列表       | 编号的待确定问题清单，便于跟踪调查                                                                                                         | 需新写（例：信用评分综设2 才实现、多端与风控接口预留范围）              |

> **后端 B**：借款申请、审批、放款、还款、逾期 → 对应用例与功能需求。
> 第四名成员（若你不在上述三人中）建议承担**统稿与评审**：统一编号、术语、图表风格，并做一致性检查。

## 五、协作约定

1. **编号规则**（先约定，避免汇总时打架）
   - 功能需求：`FR-模块代号-序号`，如 `FR-AUTH-01`、`FR-LOAN-03`
   - 非功能需求：`NFR-类别-序号`，如 `NFR-PERF-01`、`NFR-SEC-01`
   - 用例：`UC-序号`，如 `UC-01`
   - 待定问题：`Q-序号`
2. **术语统一**：一律以 `05-术语表` 为准，不得自造译名。
3. **图表统一**：统一用 **Mermaid**（本项目已有 6 张图可直接复用），配色与风格一致。
4. **优先级统一**：高 / 中 / 低三档，与 `02` §9 的 P0/P1/P2 对应（P0=高，P1=中，P2=低）。
5. **一条需求一条测试用例**：模板明确要求——若某条功能需求找不到合适的测试用例，说明该需求描述有问题。
6. **评审方式**：各部分初稿完成后交叉评审（每人评另两人的部分），由统稿人汇总修订。
